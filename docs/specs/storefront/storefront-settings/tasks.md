## Implementation notes (deviations from the plan, to fold into the spec in task 24)
- **Concurrency token:** rows use PostgreSQL `xmin` (as every other module does, `docs/db/naming.md` section 2), not a `ROW_VER` column. The draft aggregate also keeps `VER_NO` (ST-14).
- **Sibling positions:** `(PRNT_ID, SORT_SEQ)` is a plain index, not unique: a reorder is saved row by row and a unique check would fail on the intermediate state of a swap. The validator rejects duplicate positions instead.
- **Tables added to the plan's list:** `POPL_SRCH` (popular searches, a SCRUM-205 contract addition), `FACT_LKP` (the six fact keys as a lookup, referenced by `PAGE_BLCK.FACT_ID`), `DRFT_MAIN` (the draft version counter). The redirect table is `PAGE_RDIR`, the link-target lookup `LINK_TGT_LKP`, the current-snapshot column `CRNT_IND` (glossary clashes: `RDIR`, `TGT`, `CURR` = currency).
- **Delivery city:** one `DLVR_RULE` row per city (unique `CITY`); there is no separate city lookup, so a new city is a new row, not a schema change.
- **Code folders:** the API feature folder carries the spec name, `StorefrontSettings`, so `StructureSyncTests` can match it to the spec.
- **Test tooling:** `dotnet ef` runs in the SDK container from the user's global tool store (net8 tool, `DOTNET_ROLL_FORWARD=Major`); the container has no network, so restore uses `-p:NuGetAudit=false -p:RestoreSources=/root/.nuget/packages`.
- **Contract additions found while seeding (task 5), to add to the plan's "Contract additions" and the spec:** a `List` block has an `ordered` flag (`PAGE_BLCK.ORDR_IND`, `ordered` = `ORDR`); a `Table` block's caption is the block `Label`, its header row is row 0 of `PAGE_BLCK_ITM`; `LBL` on a block is 120 characters.
- **Seed vs the web fallback (open, for the owner):** the seeded pages are all `Draft` (task 5: "page drafts"), so the first publish of the seeded draft is refused until the owner fills the facts and publishes the pages (ST-17; the footer links to those pages). The storefront's built-in fallback shows six of them as `published`. They agree on wording, navigation, ages, footer and popular searches (a contract spec checks it); they differ on page status by design, and the fallback should keep serving until the first publish.
- **Seed vs the web model, mapping for the published document (tasks 9 and 11):** a navigation `Link` that has members is emitted as web kind `group` with its target; a domain `Group` (no target) as `group` without one; `CollectionList` as `collection-list`. `brand.whatsapp` is stored as E.164 (`+923315613217`, ST-4) and emitted without the `+` (`923315613217`, the web contract). The footer WhatsApp link needs `wa.me` on the external-host allow-list in configuration.
- **Placeholder facts (owner instruction, 2026-10-24):** the contact email `osamabuss048@gmail.com` is real; opening hours, the four delivery cities (times and charges), the 7-day exchange window and its three conditions are PLACEHOLDERS seeded by `SeedPlaceholderFacts` and must be replaced in the admin app before launch. Pages stay `Draft`, so nothing is published until the owner reviews it.
- **Section B decisions (tasks 6 to 11), to fold into the spec/plan in task 24:**
  - *Replace, not patch:* each save replaces its whole part (the sets are tens of rows). Navigation, ages, contact, delivery are written in two saves inside one transaction (delete, then insert) because of their unique keys. Row ids therefore change on every save; nothing outside the module holds them.
  - *Concurrency:* the draft carries one version counter; every `Save*Command` quotes the version it loaded and a stale one is a 409 (`DomainException`). Pages use their own `xmin` row version (`PageDto.RowVersion`), which also catches a change to only the blocks (`DbUpdateConcurrencyException`, 409).
  - *Popular searches* are saved by `SaveContactSettingsCommand` (the "Settings" screen), not by a command of their own.
  - *Links to draft pages:* saving accepts a link to an existing, non-archived page; publishing requires it to be published. A slug change does not rewrite links to the old slug; the owner updates them (publish names each dead link). Offered later: rewrite links on a slug change.
  - *Category targets* are refused until the Catalog category contract exists (SCRUM-207); the other target kinds work.
  - *The snapshot document* is `{ settings, pages, redirects, gone }`: `settings` in the storefront `SiteSettings` shape (disabled entries and their subtree left out, drafts left out), `pages` the published page contents, `redirects` old slug to new slug, `gone` the archived slugs and the old slugs of archived pages. Its hash ignores nothing but the version number (compared at the current version), so a repeat publish of equal content returns the existing snapshot.
  - *Restore* publishes a copy of the old snapshot as a new version (settings `version` rewritten); it does not change the draft.
  - *Public reads* come from a 60 s in-memory copy dropped by the outbox consumer of `StorefrontSettingsPublished` (the outbox table came with migration `AddOutbox`). `Storefront:AllowedExternalHosts` (default `wa.me`) is the external-link allow-list.
- **Section C decisions (tasks 12 to 15):**
  - *Routes:* public `GET /api/storefront/settings` and `GET /api/storefront/pages/{slug}` (policy `Public`, a named always-allow policy so every group still states who may call it); admin routes under `/api/admin/storefront-settings` (policy `StorefrontSettings`: role `StorefrontSettings` or `Admin`, as Catalogue and Inventory). Commands are bound straight from the request body; the page routes take the id from the route. Enums travel by name (`"Link"`, `"Path"`, `"Published"`).
  - *Public caching:* `ETag` is the snapshot hash, `Cache-Control: public, max-age=60`, and `If-None-Match` gets a 304. A page that moved answers 301 with the new API path in `Location` and `{"slug": ...}` in the body (the storefront turns it into its own 301); an archived page answers 410.
  - *Start-up guard:* `Storefront:EnableAdminRoutes` (default true). The host already refuses to start without a real authentication scheme outside Development/Testing (ADR 0011); the module repeats the check for its own routes (`StorefrontAdminRoutesGuard`) and does not map them when the switch is off. 401/403 is proved for every admin route by enumerating the real endpoint table.
  - *Sitemap source:* `IStorefrontPageQueries` in `Storefront.Contracts` lists the published pages of the current snapshot (slug, title, last modified = when that snapshot was published). The sitemap job (SEO feature) will consume it.
  - *Audit (task 14), open for the owner:* ADR 0016's `AuditRecorded` interceptor, its `[NotAudited]` attribute and the Identity consumer are Sprint 8 work and are not built (S8 is parked), so nothing here can produce them. Until then the audit columns (`INSR_*`, `UPDT_*`, actor `system` until staff login) and the snapshot note answer "who, when, why" for the publish path. **ST-12 asks for "old and new values"; ADR 0016 forbids storing values (names of changed columns only).** ADR 0016 overrides the BRD, so I have built nothing that stores values; confirm that ST-12 should be read as "which fields changed" before this task is closed.
- **Section D decisions (tasks 16 to 20), to fold into the spec/plan in task 24:**
  - *Folder and e2e names:* the web feature is `features/storefront/storefront-settings/` and its e2e file `storefront-settings.e2e.spec.ts`, because `StructureSyncTests` requires the web feature, the API feature and the spec folder to share a name (the plan said `settings`).
  - *One store, many screens:* a single NgRx feature (`storefrontSettings`) holds the draft and its version for the five part screens, the page list, the page being edited and the versions. Every part screen reloads the draft when it opens, quotes the loaded version on Save, and a 409 offers "Reload the latest settings". Edits stay in the container (a `linkedSignal` over the stored draft) until Save, so a failed save keeps them and a successful one or a reload replaces them.
  - *Reordering:* every list (navigation, ages, footer, popular searches, delivery rows, conditions, page blocks) reorders with labelled Move up / Move down buttons; the navigation also has "Make a member of the one above" and "Move out a level". No action needs dragging (WCAG 2.5.7, ST-15). Add member is refused with a visible reason on the third level.
  - *Ages:* a code that is already saved is read-only and the row cannot be removed (switch it off instead), matching the server rule.
  - *Page editor:* status changes are separate buttons that wait until edits are saved (the status call quotes the loaded row version). Empty text blocks are dropped before saving. The editor warns that renaming a live page sends the old address on (301).
  - *Publish screen:* a plain report of every field the server refused ("footer › Help › Delivery"), a note, "Preview the draft" (opens the preview JSON in a new tab; a rendered preview in the storefront needs the staff login of Sprint 8), and a two-step restore (ask, then confirm) in the page rather than a browser dialog.
  - *Unsaved-changes guard:* `unsavedChangesGuard` on the editable routes asks before leaving with unsaved edits (browser confirm).
  - *Not done here:* the rendered "Preview" on the storefront, and axe/390 px checks (task 23).
- **Section E decisions (task 21):**
  - *Wiring:* `SETTINGS_API_URL` now defaults to `/api/storefront/settings` (null still means the built-in set only). The SSR server (`server.ts`) forwards `GET /api/storefront/*` to `API_BASE_URL` (default `http://localhost:5051`; `http://api:8080` in docker compose) for both the server render and the browser; nothing else under `/api` is forwarded. Behind Cloudflare the same path can be routed to the API directly.
  - *Until the first publish:* the settings endpoint answers 404, the load fails and the storefront keeps serving the built-in launch set (source `fallback`). The page effect waits for the settings to settle and asks the pages API only when the settings came from the API (source `api`); otherwise it serves the launch pages as before. So the seeded drafts do not turn the six fallback pages into 404s before the owner publishes.
  - *Contract:* the API test `Seed_PublishedDocument_MatchesTheCommittedContractFixture` builds the document from the seeded database (preview mode, drafts shown as live) and compares it with `shared/data/contract/api-launch-document.json` (`ROMP_UPDATE_FIXTURES=1` rewrites it). The storefront spec `launch-settings.contract.spec.ts` compares that fixture with `launchSettings` and `launchPages` (navigation, ages, footer, brand, popular searches, page titles and content). Known differences: page status, business facts and `version`.
  - *Not handled:* a 301 for a renamed page is followed by the fetch client (same-origin proxy) and renders the new page at the old URL; turning it into a real 301 in the storefront is still to do.
- **Task 22 (e2e) decisions:**
  - *Set-up through the API:* the seeded pages are drafts and the first publish is refused until they are published (ST-17), so the spec publishes them (the two legal placeholders get a description) and resets the menu before it starts. The checks themselves go through the admin UI: rename an entry, add a member, save, publish with a note; edit a page paragraph, save, publish; archive and publish. The shop is polled for up to 60 s; the archived address must answer 410.
  - *Side effect (open):* after the spec runs, privacy and terms stay published in that database, so `pages.e2e.spec.ts` "ST-8 draft pages (privacy, terms) are not served until published" fails on a stack where the settings have been published. A publish cannot be undone, only superseded.
  - *Admin page load:* `goto` waits for `domcontentloaded`, not `load`, because the admin index requests Google Fonts.
- **Task 23 (accessibility) decisions:**
  - *Spec:* `e2e/storefront/storefront-settings.a11y.e2e.spec.ts` scans the eight screens plus the page editor at 390 px with axe (WCAG 2 A/AA to 2.2), checks there is no horizontal scroll and that every button, link, field and checkbox label in the main area is at least 44 px (inline text links exempt), that the primary admin nav fits, and that a navigation entry reorders by keyboard and buttons only.
  - *Fixes:* `.button--small` was 36 px: it now keeps the 44 px tap size on phones (compact from 40 rem up); links that are the main action of a table row (page titles) get the tap size in the stacked phone layout. Axe found no violations on any screen.
  - *Run against real data:* the dev admin must be on an origin the API allows (:4200 or :4201, `Cors:AllowedOrigins`); on another port the screens load empty and the scan proves nothing.
