# Code structure & naming conventions

How the admin app (`src/web/projects/admin`) and the API (`src/api`) are organised. Both are
**feature-first**: code that changes together lives together, and a new feature is a new folder,
not an edit to a shared one. Database naming is separate: see [`db/naming.md`](db/naming.md).

## 1. Web (Angular 22, standalone, NgRx)

```
src/app/
  core/                 singletons: HTTP client, API base URL, error mapping (@core/*)
  shared/               reusable dumb UI: components/, pipes/, utils/, models/   (@shared)
  features/
    <feature>/
      containers/       smart components: read the store, dispatch actions, pass data down
        <name>-page/<name>-page.container.{ts,html}
      components/       presentational: input()/output() only, OnPush, no Store, no services
        <name>/<name>.component.{ts,html,scss}
      forms/            typed FormGroup shapes + builders (<feature>.form.ts)
      models/           DTOs, view types, request values (<thing>.model.ts) + index.ts
      services/         HTTP only, no state (<feature>-api.service.ts)
      store/            <feature>.{state,actions,reducer,selectors,effects}.ts + index.ts
      utils/            pure helpers (<thing>.util.ts)
      <feature>.constants.ts   <feature>.routes.ts   <feature>.providers.ts   index.ts
  testing/              test-only helpers
```

Path aliases: `@core/*`, `@shared`, `@features/<feature>`, `@app/*`. **A feature is imported through
its `index.ts` only** (`@features/reference-data`), never by reaching into its folders. Features
may depend on `core`, `shared` and another feature's public barrel; never the reverse direction
(`core`/`shared` never import a feature).

### Naming

| Thing | File | Class / symbol |
|---|---|---|
| Container | `vendors-page.container.ts` | `VendorsPageContainer` |
| Component | `vendor-form.component.ts` | `VendorFormComponent` |
| Service | `vendor-api.service.ts` | `VendorApiService` |
| Model | `vendor.model.ts` | `VendorDto`, no `I` prefix |
| Pipe / util | `app-date.pipe.ts`, `form-errors.util.ts` | `AppDatePipe` |
| Constants | `purchase-orders.constants.ts` | `UPPER_SNAKE_CASE` |
| Spec | beside the file it tests, `*.spec.ts` | |

Selectors are `select*`; observables end in `$`; effects are functional `createEffect(..., { functional: true })`
and named `<verb><Thing>$`. Actions are `createActionGroup`s named `<Feature>PageActions` (what the
user did, past tense: `Save Submitted`) and `<Feature>ApiActions` (`Load Vendors Succeeded`).
One class or concept per file. Component selectors keep the `app-` prefix (E2E tests rely on them).

### NgRx rules

- Containers read state with `store.selectSignal(selector)` and dispatch; components never see the store.
- No `state.feature.x` outside `*.selectors.ts`. Reducers are pure; effects hold every side effect; services hold no state.
- Each feature has one state interface and `initialState` in `<feature>.state.ts`, registered under a `*_FEATURE_KEY`.
  Route-level features register in `<feature>.routes.ts` (`provideState`/`provideEffects` in the route's `providers`);
  `reference-data` registers app-wide because other features read its lookup cache.
- A store outlives its page, so the page's `Opened` action resets the state to its initial value.
- Form state (`FormGroup`) and other purely local UI state stay in the container; anything that comes from
  the server, or that survives a navigation, is in the store.
- Presentational components that need id → name lookups take a `LookupNameResolver` as an `input`.

## 2. API (.NET 10 modular monolith)

```
src/api/src/
  BuildingBlocks/  Romp.BuildingBlocks[.Application|.Persistence]     Outbox/ Inbox/ Auditing/ ...
  Modules/<Module>/
    Romp.Modules.<M>.Contracts/        public DTOs and query interfaces other modules may use
    Romp.Modules.<M>.Domain/<Feature>/           entities, value objects, domain events
    Romp.Modules.<M>.Application/<Feature>/      one file per use case (command/query + validator + handler), DTOs, mappers
    Romp.Modules.<M>.Application/Abstractions/   ports (IXxxDbContext, IFileStorage, ...)
    Romp.Modules.<M>.Infrastructure/
      Persistence/   DbContext, design-time factory, transaction behaviour
      <Feature>/     <Feature>Endpoints.cs, <Feature>Requests.cs, <Entity>Configuration.cs, query implementations
      Migrations/    generated by EF (do not move)
      <M>Module.cs   registers services and maps each feature's endpoints
  Romp.Api/          host: Program.cs, ExceptionHandling/, Seeding/
tests/  mirror the source: Romp.Modules.<M>.Tests/<Feature>/..., Support/ for helpers
```

- **Namespaces follow folders**: `Romp.Modules.Vendor.Application.PurchaseOrders`. A file's namespace is its project name plus its folder path.
- **A feature is a noun in plural** (`PurchaseOrders`, `Vendors`, `Revisions`), the same name in every layer.
  Add a feature by adding the folder to each layer it touches; do not add files to another feature's folder.
- Use-case files: `<Verb><Noun>Command.cs` / `Get<Noun>Query.cs` / `Search<Noun>Query.cs`; DTOs `<Noun>Dto.cs`; mappers `<Noun>Mapper.cs`; endpoints `<Noun>Endpoints.cs` with a `Map<Noun>Endpoints` extension.
- EF mapping is one `IEntityTypeConfiguration<T>` per entity, applied with `ApplyConfigurationsFromAssembly`. Table and column names follow `db/naming.md`.
- Module boundaries (ADR 0002) are enforced by `Romp.ArchitectureTests`; add every new module to `ModuleNames`.
- Test files are named after the type under test with `Tests` (`SendPurchaseOrderCommandHandlerTests`) and live in the feature folder of the code they cover.

## 3. Adding a feature (checklist)

1. Spec, plan, tasks (see `CLAUDE.md`).
2. API: Domain → Application (use cases) → Infrastructure (configuration, endpoints) → register in `<M>Module.cs` → tests in `tests/.../<Feature>/`.
3. Web: `features/<feature>/` with `models`, `services`, `store`, `components`, `containers`, `<feature>.routes.ts`, then one lazy route in `app.routes.ts`.
4. Unit tests beside the code; an E2E spec in `src/web/e2e` for the user flow.

## 4. Lists, paging and queries (required)

- **Every list endpoint that can grow returns a page**, never the whole table: query params `page` and `pageSize`,
  response `PagedResult<T>` (`Romp.BuildingBlocks.Application.Paging`: `Items, Page, PageSize, TotalCount, TotalPages`).
  Page size defaults to 25 and is clamped to 1..100. Use `ToPagedResultAsync` on a query that is already ordered by a
  unique key (`OrderBy(name).ThenBy(id)`). Small, bounded lookups (`REF` lists) may stay unpaged.
- **Project list rows in SQL** (`Select(x => new RowDto(...))`); never load entities to map them in memory.
- **No N+1**: no query inside a loop, no lazy loading. Load related rows with `Include` (use `AsSplitQuery` when
  including two or more collections where the project allows it) or one bulk query filtered by `Contains`.
- **Web lists** keep `total`, `page`, `pageSize` in the feature store; changing a filter resets to page 1; the UI uses
  `<app-pagination>` from `@shared`. A pick-list that needs every row uses `fetchAllPages`.
- **Tests**: a paged endpoint needs a test for ordering across pages and for clamping; E2E specs must not assume a
  row is on page 1: find it through the list's search or filter.

## 5. Working rules for every session

- Read this file and `CLAUDE.md` before adding a feature; new code follows the structure above without asking.
- Verify before saying done: `ng test admin`, `ng build admin`, `dotnet test` (in the Docker SDK container on the
  dev machine), and the Playwright suite against `docker compose up -d --build api admin` for anything user-visible.
- Adding a module: add it to `ModuleNames` in `Romp.ArchitectureTests`. Changing entities: confirm
  `dotnet ef migrations has-pending-model-changes` is clean or add a migration.
